# 캡스톤 최종 소프트웨어 구성과 개발 계획

기준일: 2026-11-24. 이 문서는 현재 로컬 시연과 최종 제품의 화면·서버 역할을 정의한다. 진행 상태와 완료 기준은 [개발 체크리스트](implementation-checklist.md), 데이터 형식은 [공통 계약](contracts/recommendation-v1.md), 시뮬레이션 동작은 [시뮬레이션 명세](design.md)를 따른다.

## 현재 개발 방향

- 현장 평가는 수동 종료까지 계속 실행하는 연속 시연을 기본으로 한다. 평가 중에는 연속 실행에서 사용자 이동·대기·탑승 상태를 이어 간다.
- 연속 시연의 인원·보충·개인 체류·배속은 `lotteworld/configs/continuous.json`에서 설정한다.
- 장시간 시연에서 인원이 무한히 누적되지 않도록 목표 상한과 개인 체류 만료, 빈자리 보충을 적용한다. 현장 평가 시간은 **2시간**이며 해당 구간을 포함하도록 최소 2시간 연속 실행을 검증한다. 서버는 수동 종료까지 계속 실행한다. [연속 시연 설정](../lotteworld/docs/configuration.md#연속-시연-설정과-상태)
- 로컬 시연은 시뮬레이션과 운영자 대시보드를 한 앱의 두 탭으로 제공한다. QR 사용자 웹은 시뮬레이션의 예상 대기와 시설 운영 상태를 추천에 사용한다. 현장 영상·혼잡 분석 연동과 AWS 배포는 후속 단계다.

## QR 기반 가상 사용자 시연

시연 관람객이 공통 QR로 접속하면 로컬 서버가 브라우저별 세션과 시뮬레이션 캐릭터를 연결한다. 캐릭터는 서쪽 안내판 `[123, 111]`m에서 입구 다리 쪽의 빈 보행 위치에서 시작한다. 실제 제작할 표지판에는 자이로스핀·혜성특급·자이로드롭을 각각 가리키는 방향 안내판 세 개가 있다. 기본 시연에서는 세 시설 모두 정상 운행하며 QR 웹에 저장한 순위를 사용해 추천을 계산한다. 마지막 QR 진입이나 세션 조회 후 5분 안에 같은 브라우저로 돌아오면 캐릭터와 저장 순위를 복구한다. [로컬 실행 방법](../lotteworld/README.md#qr-사용자-진입과-선호-입력)

추천 서버는 선호 순위, 캐릭터의 현재 가상 위치, 시설별 예상 대기와 이용 가능 상태를 반영한다. 수락하면 캐릭터가 시설로 이동하고, 실제로 줄에 합류하면 대기 인원에 포함된다. 사용자 웹과 시뮬레이션 웹은 같은 캐릭터의 위치와 이용 상태를 표시한다. 하차 후 현재 위치와 대기 현황으로 다음 시설을 추천한다.

캐릭터 위치는 가상 좌표다. 보상은 후속 기능이며 서버가 유효한 수락을 확정했을 때 한 번 지급하는 계획이다. 시연 배속은 내부 실행 설정으로 관리한다. 시뮬레이션 기본 화면은 3D 지도를 중심으로 구성한다. [체크리스트](implementation-checklist.md)

배경 방문객의 유입·이동·대기·시설 운행은 연속 시연 엔진이 처리한다. QR 사용자 추천은 이 엔진을 조회한다. 추천 입력과 결과의 구조는 [공통 계약 예제](contracts/recommendation-v1.md)로 검증한다.

## QR 사용자 웹과 통합 운영 앱의 역할

QR 참여자는 모바일 사용자 웹을 쓰고, 시연자는 통합 운영 앱에서 전체 가상 공간과 운영 지표를 본다. 운영 앱은 ‘시뮬레이션’과 ‘운영자 대시보드’ 두 탭으로 구성한다.

| 구분 | 대상·목적 | 주요 기능 | 상세 문서 |
| --- | --- | --- | --- |
| 사용자 웹 | QR로 접속한 참여자가 자신의 추천을 수락하고 상태 확인 | 선호 입력·추천/수락·수락 보상·자기 캐릭터 중심 3D 지도 | [사용자 웹](user-web.md) |
| 시뮬레이션 탭 | 평가자·시연자가 전체 가상 공간을 관찰 | 전체 방문객·줄·운행·QR 캐릭터를 표시하는 연속 3D 맵. 시간 표시·재생바 없음 | [시뮬레이션 웹](simulation-web.md) |
| 운영자 대시보드 탭 | 시연자가 시설 운영과 전체 흐름을 확인 | 시설별 대기·혼잡·차량 상태, 방문객 흐름, 안내판 상세 | [운영자 탭](simulation-web.md#운영자-대시보드-탭) |
| 공통 서버·엔진 | QR 사용자 웹과 운영 앱에 같은 실행 상태를 제공 | 추천·수락 검증·보상·세션과 엔진의 위치/진행 상태 연결 | [공통 데이터 계약](contracts/recommendation-v1.md) |

기존 3D 지도·시설 자원과 서버의 같은 캐릭터 상태는 공유한다. 사용자 웹은 자기 캐릭터·목적지·경로와 추천·보상에 집중하고, 시뮬레이션 웹은 전체 공간을 보여준다. 수락 보상 지급 상태는 후속 단계에서 QR 사용자 웹에 표시한다. 시간 표시·재생바를 제외하는 기준은 시뮬레이션 기본 시연 화면에 적용하며 사용자 웹의 예상 대기와 갱신 상태는 유지한다.

로컬 Python 서버는 시뮬레이션 `/`, 운영자 대시보드 `/operator`, 사용자 웹 `/user?sign_id=magic-island-west`를 제공한다. 시뮬레이션과 운영자 대시보드는 같은 페이지에서 탭으로 전환한다. 브라우저 모바일 에뮬레이션에서 캐릭터 이동과 두 지도의 상태 연동을 확인했다. 실제 휴대폰의 조작·성능과 현장 운영 앱의 접근 권한은 후속 검증 범위다. [QR 검증](verification/qr-user-entry-and-preferences.md)

## 로컬 개발과 AWS 배포

현재 로컬 시연의 세 화면과 공통 API를 같은 서버에서 배포한 뒤, 실제 휴대폰의 QR 접속과 다중 사용자·장시간 시연을 검증한다. [배포 체크리스트](implementation-checklist.md#배포와-실기기-확인)

서버 주소·포트·저장 경로·저장소 연결 정보를 실행 설정으로 분리한다. 배포 서비스·DB·컨테이너 사용 여부는 미정이며 IAM 권한을 확인한 뒤 정한다. 권한은 주로 배포·운영 구성에 영향을 주며 추천 로직·공통 계약·두 웹의 역할은 유지한다. 학교 지원 계정의 허용 서비스·리전·사용 한도·기한은 아직 확인하지 않았다. 기존 지도 서버의 `127.0.0.1` 바인딩만으로 휴대폰 외부 접속이 가능한 상태는 아니다.

하드웨어 자체 제작은 소프트웨어 결과물과 구분한다. 그러나 하드웨어의 영상을 받는 서버 연동은 최종 소프트웨어 범위에 포함한다. 기존 아쿠아리움 `web-admin`은 참고 가능한 정적 시안이며, 해당 폴더의 해양 시설·가상 추천·고정 대기시간이 최종 제품을 대신하지 않는다. 안내판의 출력 콘텐츠·원격 제어는 이번 설명만으로 추가 확정하지 않는다. 퍼레이드 관람 이동은 별도 범위다.

## 지도 요구사항

요구된 지도는 기존 아쿠아리움의 3D 방식과 실제 매직아일랜드 안내도의 시각적 배치를 결합한 화면이다. 3D 표시와 지도 연결을 검증했다. [3D 검증 기록](verification/magic-island-map3d.md)

- 안내도의 섬 윤곽, 호수, 오른쪽 아래 다리, 중앙 매직캐슬과 광장, 시설 간 상대 위치·방향을 3D 공간으로 재구성한다. 주 섬과 남쪽 메이플 돌출부, 다리 양옆 수면 홈을 구분하고 성 정면·앞 광장·사선 다리를 같은 직선 축으로 연결한다.
- 아트란티스의 물길·코스터, 자이로드롭의 탑, 자이로스윙의 지지대·진자, 자이로스핀의 디스크·레일, 혜성특급의 지상 열차·굽은 코스, 아르카나라이드의 소형 순환 시설을 식별 가능한 입체 형상으로 표현한다. 정밀 복제품·실측 디지털 트윈을 요구한다는 뜻은 아니다.
- 보행로·입출구·대기 구획을 3D 형상과 같은 미터 좌표에 연결하고, 장식·시설 형상이 실제 이동 가능 통로를 가리지 않는지 검사한다. 배치를 조정하면 경로 거리·경계 검사도 다시 실행한다.
- 전체 보기에서 안내도와 대조해 배치를 알아볼 수 있어야 한다. 회전·확대·이동·시점 복귀와 시설 확대·가림 줄이기를 지원한다. 혜성특급은 다른 시설처럼 지상에 표시하며 지하 절개·B1 표시는 사용하지 않는다. 섬의 포장 광장은 보행 공간으로 잇고 해안 녹지와 내부 화단은 보행 제한 구역으로 둔다.
- 기존 `aquarium/web/map3d.js`의 Three.js·직교 카메라·OrbitControls·시설 선택·다수 보행자 표시 방식을 참고한다. 재사용 시 롯데월드 안에 독립적으로 구성하고 출처·수정 내용을 기록한다. 아쿠아리움 런타임을 직접 참조하지 않는다.

6개 시설은 같은 지도 좌표와 시설 ID로 표현하고 경로·형상 검사를 거친다. 설정 검증 출력은 `map_ready`와 `runnable: false`, 실행 중 `/api/meta`는 `continuous_running`과 `runnable: true`를 반환한다. [설정 계약](../lotteworld/docs/configuration.md)

## 통합 운영 앱

하나의 페이지에서 ‘시뮬레이션’(`/`)과 ‘운영자 대시보드’(`/operator`)를 전환한다. 시뮬레이션 탭은 전체 3D 지도를 보여 주고, 대시보드 탭은 시설별 대기·탑승·혼잡, 방문객 흐름과 안내판 정보를 표시한다. 두 탭은 같은 `/api/meta`와 `/api/state`를 사용하며, 탭 전환 시 지도 시점과 시설 선택을 이어 간다. [탭 화면과 동작](simulation-web.md#운영자-대시보드-탭)

현장 연동 단계에서는 운영자 대시보드에 안내판별 영상·연결 상태와 관측 지표를 연결한다. 통합 앱에서도 관측값과 시뮬레이션 값을 출처·기준 시각으로 식별한다. 시뮬레이션은 실행 ID를 사용하고, 현장 영상 조회는 관리자 권한으로 제공한다. 실험 조건과 결과를 비교하는 화면은 추천 효과 평가 단계에서 검토한다.

## 서버의 데이터 흐름과 계산 경계

1. 표지판·카메라 식별자로 영상과 촬영 시각을 수신한다. 표지판 위치, 관측 구역, 지도 버전의 대응을 관리한다.
2. 서버에서 사람 수를 추정하고 해당 관측 구역의 인원·품질·갱신 상태를 기록한다. 영상이 끊겼을 때 이전 값을 현재 관측처럼 계속 제공하지 않는다.
3. 실제 보행 면적을 보정한 경우 `인원 / 유효 면적(m²)`으로 밀집도를 계산한다. 면적 보정 전에는 인원 추정 또는 혼잡 수준으로 표시하고 `명/m²`의 실측 밀집도로 주장하지 않는다. 서로 겹치는 카메라의 인원을 단순 합산하지 않는다.
4. 별도 대기시간 추정기가 시설 상태·관측 가능한 대기 정보·처리량 가정으로 예상 대기를 계산한다. 통로의 인원이나 밀집도만으로 놀이시설 대기시간을 확정하지 않는다. 자료가 없으면 미집계 또는 가정 기반 추정임을 표시한다.
5. 추천 서비스가 관람객 선호·출발 지점·보행 거리·예상 대기·시설 이용 가능 상태·구역 혼잡을 함께 고려해 경로를 반환한다. 혼잡을 피하려고 이동거리나 대기가 과도하게 증가하지 않는지 비교한다. 추천을 따르는 인원이 한 경로에 다시 몰리는 경우도 시뮬레이션에서 검증한다.
6. 관람객은 추천과 예상 대기를 보고, 관리자는 같은 기준 시각의 영상·관측·시설 현황을 확인한다. 영상은 관람객 화면에 제공하지 않는다.

시연에서는 QR 접속 후 지정 표지판을 초기 출발 지점으로 사용하고, 이후 위치는 시뮬레이션 캐릭터의 좌표를 사용한다. QR만으로 사용자의 지속적인 실제 위치를 알아낼 수는 없다. 실제 현장 서비스의 이동 후 위치 입력 방식은 별도로 검토한다.

시뮬레이션은 이 서버에 사용할 상태 공급 방식 중 하나다. 추천·대기시간 계산을 화면마다 따로 구현하지 않고 같은 인터페이스로 연결한다. 현장 영상 관측과 시뮬레이션의 정답 인원을 구분해 관측 오차와 추천 효과를 평가할 수 있게 한다. 실시간 영상 서비스에 실제 사람 한 명마다 시뮬레이션 개체가 존재한다고 가정하지 않는다.

## 먼저 맞출 공통 계약

추천·시뮬레이션의 JSON 필드·단위·상태 전이와 기준 정책은 공통 계약 v1에 정의했다. 로컬 시연 서버는 지도·시설 상태 조회와 QR 진입·조회·선호 저장·추천·수락 API를 제공한다. 아래 표는 현장 관측과 추천 효과 평가까지 연결할 때 필요한 정보다. 영상·관측 API, 전송 방식, 저장 방식과 분석 모델은 후속 설계에서 정한다. [공통 데이터 계약 v1](contracts/recommendation-v1.md) · [로컬 API](../lotteworld/README.md#qr-사용자-진입과-선호-입력)

| 계약 | 필요한 정보 |
| --- | --- |
| 시설·지도·표지판 | 시설 ID, 표지판·카메라 ID, 지도 버전, 위치, 관측 구역과 보정 면적 |
| 관측 상태 | 출처, 촬영·수신·분석 시각, 관측 구역, 추정 인원, 밀집도 산출 가능 여부, 품질·오래된 데이터 상태 |
| 시설 상태·예상 대기 | 운행·점검·미확인 상태, 예상 대기 분, 기준 시각, 관측·모형·수동 입력 등 근거, 추정 불가 상태 |
| 추천 | 선호, 출발 지점, 대상 시설, 고려한 혼잡·대기 상태 버전, 경로, 이동·대기 예상값, 기준 시각과 추천 이유 |
| 실험 | 실행 ID·설정/지도 해시·시드·재생 시각, 관측 오차·추천 정책·추종률 실험 조건, 정확한 논리 인원 |
| 영상 조회 | 해당 표지판과 영상 소스의 대응, 최근 프레임·촬영 시각·연결 상태, 관리자 조회 경계 |

## 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 3D 안내도 구현 (완료) | 안내도 배치·입체 형상·카메라 조작과 실제 이동 좌표 연결을 함께 확인 |
| 2 | 공통 상태·추천 계약 및 추천 정책 | 계약 문서와 예제로 입력·결과를 검증한다. 선호, 예상 대기, 가상 위치에서의 이동 거리를 평가한다. [공통 데이터 계약](contracts/recommendation-v1.md) |
| 3 | 연속 시연 엔진 및 서버 연동 | 유입·퇴장·대기열·운행·반복 이용·배속·장시간 실행을 검증하고, 시뮬레이션 상태에 추천·수락·이동을 연결 |
| 4 | 영상 입력·인원 추정과 표지판 대응 | 표지판별 영상 수신·촬영 시각·구역 대응, 표본 정답과 사람 수 오차 평가, 단절·지연 처리. 녹화 영상 검증과 실제 장치 연동을 구분 |
| 5 | QR 사용자 웹과 통합 운영 앱 | 로컬 시연에서 QR 세션·선호·실시간 추천과 수락, 두 3D 화면의 캐릭터 연동, 운영자 대시보드 탭을 구현했다. 수락 보상 지급과 안내판 영상 연동은 후속 작업이다. |
| 6 | 전체 연결과 추천 효과 평가 | 영상 변화 → 관측 갱신 → 추천 변화 → 양쪽 화면 반영을 검증. 안내 없음/추천 적용을 같은 수요·시설 조건에서 비교하고 관측 오차·갱신 지연도 평가 |

계약 예제로 추천 정책을 검증하고, QR 화면에서 사용하는 시뮬레이션 연동과 영상 연동은 각각 검사한다. 단계 3의 장시간 연속 실행 검증은 엔진 범위의 완료이며 최종 제품 전체 완료가 아니다. 추천 효과의 실험은 실제 추천 서비스와 연결한 뒤 별도로 수행한다.

## 남은 결정

### 시연 배포와 부하

- **시연 배경 방문객 수** — 기본값 1,500명과 후보 1,300명을 같은 시드·배속에서 비교한 뒤 적용 인원을 정한다.
- **AWS 배포 구성** — 학교 계정의 권한·허용 리전·사용 한도를 확인한 뒤 사용할 서비스와 DB·컨테이너 사용 여부를 정한다.

### 현장 연동과 보상

- **표지판과 영상 분석** — 표지판·카메라의 수와 설치 위치, 시야·관측 구역, 영상 전송·보관 방식과 보관 기간, 인원 추정 모델과 분석 주기를 정한다. 유효 면적 보정과 카메라 중복 구역 처리 방법도 정한다.
- **실제 시설 상태와 추천** — 시설 운영·점검 상태의 입력 주체, 예상 대기의 출처·추정 방식, QR 진입 후 위치 갱신 방식, 영상 누락 시 대체 규칙을 정한다. 현장 데이터의 유효기간·추천 가중치·QR 세션 수명은 현장 적용 단계에서 검토한다. 로컬 시연의 QR 세션은 5분이며 `sign-baseline-v1`은 서쪽 안내판의 세 시설을 평가한다.
- **수락 보상** — 유효한 추천 수락이 확정되면 한 번 지급하는 기준으로, 지급량·한도·취소와 회수 규칙을 정한다.
- **관리자 접근** — 현장 운영자 인증 방식과 영상 조회 권한을 정한다.
