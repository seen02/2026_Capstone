# 캡스톤 최종 소프트웨어 구성과 개발 계획

기준일: 2026-11-18. 사용자가 설명한 최종 결과물을 기준으로 정리했다. 이 문서는 전체 제품의 방향과 화면·서버 역할을 정의한다. 다음 구현 범위와 완료 기준은 [개발 체크리스트](implementation-checklist.md), 데이터 형식은 [공통 계약](contracts/recommendation-v1.md), 기존 지도·시설과 이전 시간표 근거는 [시뮬레이션 명세](design.md)를 따른다. 아래 항목은 구현 완료 보고가 아니다.

## 현재 개발 방향

- 현장 평가는 수동 종료까지 계속 실행하는 연속 시연을 기본으로 한다. 평가 도중 사용자 이동·대기·탑승·보상 상태를 시간표 종료나 반복 재생 때문에 초기화하지 않는다.
- 기존 10:00–19:00·총유입 10,350명은 설정 검증까지 준비된 이전 계획이다. 해당 시간표의 실행 엔진은 없으며 현재 우선 개발 조건에서 제외한다. 별도 9시간 비교 실험 모드의 개발도 지금 확정하지 않는다.
- 장시간 시연에서 인원이 무한히 누적되지 않도록 목표 상한과 개인 체류 만료, 빈자리 보충을 적용한다. 현장 평가 시간은 **2시간**이며 해당 구간을 포함하도록 최소 2시간 연속 실행을 검증한다. 서버는 수동 종료까지 계속 실행한다. [연속 시연 설정](../lotteworld/docs/configuration.md#연속-시연-설정과-상태)
- 추천 서버를 로컬에서 먼저 최소 구현·검증한다. AWS 계정 수령이나 권한 확인을 개발 선행 조건으로 두지 않는다.

## QR 기반 가상 사용자 시연

시연 관람객이 공통 QR로 접속하면 로컬 서버가 브라우저별 세션과 시뮬레이션 캐릭터를 연결한다. 캐릭터는 가상 표지판 `[101, 149]`m 주변의 보행 구역에서 시작한다. 실제 제작할 표지판에는 자이로스핀·혜성특급·자이로드롭을 각각 가리키는 방향 안내판 세 개가 있다. 기본 시연에서는 세 시설 모두 정상 운행하며 QR 웹에 저장한 순위를 사용해 추천을 계산한다. 재접속하면 같은 캐릭터와 저장 순위를 조회한다. [로컬 실행 방법](../lotteworld/README.md#qr-사용자-진입과-선호-입력)

추천 서버는 선호 순위, 캐릭터의 현재 가상 위치, 시설별 예상 대기와 이용 가능 상태를 고려해 다음 놀이기구 한 곳과 추천 이유를 제공한다. 사용자의 유효한 추천 수락이 확정되면 웹에 수락 보상을 지급하고 시뮬레이션 캐릭터가 해당 시설로 이동한다. 웹에도 같은 캐릭터의 상태를 표시한다. 이후 이용 완료 시 갱신된 위치와 대기 현황으로 다시 추천한다. 이동·탑승·이용 완료는 보상 지급 조건이 아니다. 수락 인원이 이후 혼잡에 미치는 영향도 반영한다.

위치는 실제 GPS가 아닌 시뮬레이션 좌표다. 보상은 추천 수락에 대한 보상이다. 같은 추천 수락에 중복 지급하지 않으며 실제 시설 이용 인증과 구분한다. 시연에 적합한 배속은 내부 실행 설정으로 관리한다. 시뮬레이션 웹의 기본 시연 화면에는 경과 시간·시계·재생바를 표시하지 않는다. 관련 구현 항목은 [체크리스트](implementation-checklist.md)의 공통 서버·사용자 웹·시뮬레이션 웹 구분을 따른다.

현재 지도는 준비됐지만 방문객 유입·이동·대기·시설 운행 엔진은 미구현이다. 따라서 추천 로직과 서버를 먼저 구현할 때는 공통 상태 계약과 출처가 명시된 모의 대기 현황을 사용해 검증한다. 이후 시뮬레이션 상태 공급자로 교체하고, 영상 분석 연동은 별도 단계로 검증한다.

2026-11-17에 기존 시설 ID·좌표·지도 경로 코드와 대조한 [공통 데이터 계약 v1](contracts/recommendation-v1.md)을 작성했다. 선호 순위와 가상 위치, 대기 현황의 출처·기준 시각·미집계 상태, 추천과 수락 이후의 상태 전이, 모의 데이터에서 시뮬레이션 데이터로 교체할 경계를 정의했다. JSON 예제는 구조 검증용이며 실제 엔진 실행 결과가 아니다. 다음으로 모의 현황을 사용하는 추천 로직·서버, QR 사용자와 캐릭터 연결, 추천 수락·보상과 시뮬레이션 엔진 연동 순으로 진행한다. 단계 간 필요한 최소 기능은 연동하면서 조정한다.

## 사용자 웹과 시뮬레이션 웹의 역할

두 웹은 목적·화면·조작을 구분한다. 문서에서 ‘사용자 웹’은 QR 참여자의 모바일 화면, ‘시뮬레이션 웹’은 전체 가상 공간을 보여주는 시연 화면을 뜻한다. 상세 요구사항과 각 화면의 완료 기준은 아래 전용 문서에서 관리한다.

| 구분 | 대상·목적 | 주요 기능 | 상세 문서 |
| --- | --- | --- | --- |
| 사용자 웹 | QR로 접속한 참여자가 자신의 추천을 수락하고 상태 확인 | 선호 입력·추천/수락·수락 보상·자기 캐릭터 중심 3D 지도 | [사용자 웹](user-web.md) |
| 시뮬레이션 웹 | 평가자·시연자가 전체 가상 공간을 관찰 | 전체 방문객·줄·운행·QR 캐릭터를 표시하는 연속 3D 맵. 시간 표시·재생바 없음 | [시뮬레이션 웹](simulation-web.md) |
| 공통 서버·엔진 | 두 웹이 사용할 같은 세계의 데이터를 제공 | 추천·수락 검증·보상·세션과 엔진의 위치/진행 상태 연결 | [공통 데이터 계약](contracts/recommendation-v1.md) |

기존 3D 지도·시설 자원과 서버의 같은 캐릭터 상태는 공유한다. 사용자 웹은 자기 캐릭터·목적지·경로와 추천·보상에 집중하고, 시뮬레이션 웹은 전체 공간을 보여준다. 보상 지급은 사용자 웹에 표시하고 시뮬레이션 웹에는 개별 보상 조작을 두지 않는다. 시간 표시·재생바를 제외하는 기준은 시뮬레이션 기본 시연 화면에 적용하며 사용자 웹의 예상 대기와 갱신 상태는 유지한다.

두 웹은 별도 화면·진입점으로 구분하되, URL·배포 단위·인증·상태 전송 방식은 후속 구현에서 정한다. 서버를 두 개로 만들거나 지도를 따로 만드는 요구사항은 아니다. 사용자 웹의 모바일 3D 조작·성능과 두 화면의 동기화는 아직 검증하지 않았다. 관리자 대시보드와 시뮬레이션 웹의 앱 통합 제안은 이 구분과 별개의 미정 사항이다.

## 로컬 개발과 AWS 배포

로컬에서 모의 시설 현황으로 추천 API를 먼저 구현하고, 최소 동작을 검증한 시점에 AWS 1차 배포와 휴대폰 접속을 확인한다. 전체 시뮬레이션 완성을 첫 배포의 선행 조건으로 두지 않는다. 이후 사용자 세션·수락/보상·3D 위치 표시와 엔진을 기능별로 연결하고 장시간·다중 사용자 시연을 검증한다.

서버 주소·포트·저장 경로·저장소 연결 정보를 실행 설정으로 분리한다. 배포 서비스·DB·컨테이너 사용 여부는 미정이며 IAM 권한을 확인한 뒤 정한다. 권한은 주로 배포·운영 구성에 영향을 주며 추천 로직·공통 계약·두 웹의 역할은 유지한다. 학교 지원 계정의 허용 서비스·리전·사용 한도·기한은 아직 확인하지 않았다. 기존 지도 서버의 `127.0.0.1` 바인딩만으로 휴대폰 외부 접속이 가능한 상태는 아니다.

하드웨어 자체 제작은 소프트웨어 결과물과 구분한다. 그러나 하드웨어의 영상을 받는 서버 연동은 최종 소프트웨어 범위에 포함한다. 기존 아쿠아리움 `web-admin`은 참고 가능한 정적 시안이며, 해당 폴더의 해양 시설·가상 추천·고정 대기시간이 최종 제품을 대신하지 않는다. 안내판의 출력 콘텐츠·원격 제어는 이번 설명만으로 추가 확정하지 않는다. 비상 대피·퍼레이드 관람 이동도 별도 범위다.

## 지도 요구사항

요구된 지도는 기존 아쿠아리움의 3D 방식과 실제 매직아일랜드 안내도의 시각적 배치를 결합한 화면이다. 현재 3D 표시·연결 검증을 완료했다. [3D 검증 기록](verification/magic-island-map3d.md)을 기준으로 한다. 관리자 앱 통합을 포함한 아래 미정 사항은 이번 지도 작업에서 결정하지 않았다.

- 안내도의 섬 윤곽, 호수, 오른쪽 아래 다리, 중앙 매직캐슬과 광장, 시설 간 상대 위치·방향을 3D 공간으로 재구성한다. 주 섬과 남쪽 메이플 돌출부, 다리 양옆 수면 홈을 구분하고 성 정면·앞 광장·사선 다리를 같은 직선 축으로 연결한다.
- 아트란티스의 물길·코스터, 자이로드롭의 탑, 자이로스윙의 지지대·진자, 자이로스핀의 디스크·레일, 혜성특급의 지상 열차·굽은 코스, 아르카나라이드의 소형 순환 시설을 식별 가능한 입체 형상으로 표현한다. 정밀 복제품·실측 디지털 트윈을 요구한다는 뜻은 아니다.
- 보행로·입출구·대기 구획을 3D 형상과 같은 미터 좌표에 연결하고, 장식·시설 형상이 실제 이동 가능 통로를 가리지 않는지 검사한다. 배치를 조정하면 경로 거리·경계 검사도 다시 실행한다.
- 전체 보기에서 안내도와 대조해 배치를 알아볼 수 있어야 한다. 회전·확대·이동·시점 복귀와 시설 확대·가림 줄이기를 지원한다. 혜성특급은 다른 시설처럼 지상에 표시하며 지하 절개·B1 표시는 사용하지 않는다. 섬 내부 대부분은 보행 가능한 포장 광장으로 두고 나무는 작은 식재 구획 안에만 배치한다.
- 기존 `aquarium/web/map3d.js`의 Three.js·직교 카메라·OrbitControls·시설 선택·다수 보행자 표시 방식을 참고한다. 재사용 시 롯데월드 안에 독립적으로 구성하고 출처·수정 내용을 기록한다. 아쿠아리움 런타임을 직접 참조하지 않는다.

6개 시설 ID, 설정 분리, 경로 계산·형상 검사 기반은 유지할 수 있다. 현재 좌표·외곽은 3D 배치에 맞춰 조정했으며 후속 줄·이동 검증에서 필요한 변경은 허용한다. `map_ready`·`map_view: guide-map-3d`는 지도 자료·3D 표시 준비 상태이고 시뮬레이션 실행 가능 여부는 `runnable: false`로 구분한다.

## 시뮬레이션과 관리자 화면 통합 판단

**설계 제안: 하나의 운영자 앱 안에 ‘현장 현황’과 ‘시뮬레이션’ 탭을 두되, 데이터와 조작 권한은 분리한다.** 앱 통합은 아직 확정되지 않았고 구현 전 화면 구성·데이터 계약에서 재검토한다. 모듈 경계를 지키면 나중에 별도 앱으로 분리해도 핵심 계산을 다시 만들 필요가 없다.

| 지표 카드·혼잡 범례·데이터 갱신 표시 | 실제 시각과 시뮬레이션 재생 시각 |
| 추천 계산 인터페이스·대기시간 추정 인터페이스 | 영상 관측 인원과 시뮬레이션의 정확한 논리 인원 |
| 운영자 탐색 메뉴와 기본 화면 구조 | 현장 조회와 실험 시작·초기화·배속·되감기 |

현장 화면에는 표지판별 영상과 현재 관측·추정치를 우선한다. 시뮬레이션 기본 시연 화면에는 3D 지도를 우선하고 시간 표시·재생바는 두지 않는다. 실험 조건·결과 비교 UI는 후속 평가 기능으로 별도 검토한다. 두 화면을 하나의 거대한 화면에 항상 펼칠 필요는 없다. 같은 3D 지도 컴포넌트를 재사용할 수 있으나 관리자 화면에 항상 3D를 강제하는지는 사용성 확인 후 결정한다. 관람객 화면은 모바일 동선으로 별도 구성한다.

실험 초기화·되감기가 현장 상태나 실제 관람객 추천을 바꾸면 안 된다. 모든 상태 응답에서 현장·시뮬레이션·데모 출처와 기준 시각을 구분하고, 실험에는 실행 ID를 둔다. 관리자 영상 보기는 관리자 접근 범위로 제공한다.

## 서버의 데이터 흐름과 계산 경계

1. 표지판·카메라 식별자로 영상과 촬영 시각을 수신한다. 표지판 위치, 관측 구역, 지도 버전의 대응을 관리한다.
2. 서버에서 사람 수를 추정하고 해당 관측 구역의 인원·품질·갱신 상태를 기록한다. 영상이 끊겼을 때 이전 값을 현재 관측처럼 계속 제공하지 않는다.
3. 실제 보행 면적을 보정한 경우 `인원 / 유효 면적(m²)`으로 밀집도를 계산한다. 면적 보정 전에는 인원 추정 또는 혼잡 수준으로 표시하고 `명/m²`의 실측 밀집도로 주장하지 않는다. 서로 겹치는 카메라의 인원을 단순 합산하지 않는다.
4. 별도 대기시간 추정기가 시설 상태·관측 가능한 대기 정보·처리량 가정으로 예상 대기를 계산한다. 통로의 인원이나 밀집도만으로 놀이시설 대기시간을 확정하지 않는다. 자료가 없으면 미집계 또는 가정 기반 추정임을 표시한다.
5. 추천 서비스가 관람객 선호·출발 지점·보행 거리·예상 대기·시설 이용 가능 상태·구역 혼잡을 함께 고려해 경로를 반환한다. 혼잡을 피하려고 이동거리나 대기가 과도하게 증가하지 않는지 비교한다. 추천을 따르는 인원이 한 경로에 다시 몰리는 경우도 시뮬레이션에서 검증한다.
6. 관람객은 추천과 예상 대기를 보고, 관리자는 같은 기준 시각의 영상·관측·시설 현황을 확인한다. 영상은 관람객 화면에 제공하지 않는다.

시연에서는 QR 접속 후 지정 표지판을 초기 출발 지점으로 사용하고, 이후 위치는 시뮬레이션 캐릭터의 좌표를 사용한다. QR만으로 사용자의 지속적인 실제 위치를 알아낼 수는 없다. 실제 현장 서비스의 이동 후 위치 입력 방식은 별도로 검토한다.

시뮬레이션은 이 서버에 사용할 상태 공급 방식 중 하나다. 추천·대기시간 계산을 화면마다 따로 구현하지 않고 같은 인터페이스로 연결한다. 현장 영상 관측과 시뮬레이션의 정답 인원을 구분해 관측 오차와 추천 효과를 평가할 수 있게 한다. 실시간 영상 서비스에 실제 사람 한 명마다 시뮬레이션 개체가 존재한다고 가정하지 않는다.

## 먼저 맞출 공통 계약

아래는 설계 항목이며 현재 제공하는 API 목록이 아니다. 추천·시뮬레이션의 JSON 필드·단위·상태 전이와 개발용 기준 정책은 [공통 데이터 계약 v1](contracts/recommendation-v1.md)에 정의했다. HTTP 경로·프레임워크·DB·영상 전송 방식·모델은 아직 정하지 않았다. 영상·표지판 관측 계약은 v1의 가상 상태 계약과 구분해 후속 설계한다.

| 계약 | 필요한 정보 |
| --- | --- |
| 시설·지도·표지판 | 시설 ID, 표지판·카메라 ID, 지도 버전, 위치, 관측 구역과 보정 면적 |
| 관측 상태 | 출처, 촬영·수신·분석 시각, 관측 구역, 추정 인원, 밀집도 산출 가능 여부, 품질·오래된 데이터 상태 |
| 시설 상태·예상 대기 | 운행·점검·미확인 상태, 예상 대기 분, 기준 시각, 관측·모형·수동 입력 등 근거, 추정 불가 상태 |
| 추천 | 선호, 출발 지점, 대상 시설, 고려한 혼잡·대기 상태 버전, 경로, 이동·대기 예상값, 기준 시각과 추천 이유 |
| 실험 | 실행 ID·설정/지도 해시·시드·재생 시각, 관측 오차·추천 정책·추종률 실험 조건, 정확한 논리 인원 |
| 영상 조회 | 해당 표지판과 영상 소스의 대응, 최근 프레임·촬영 시각·연결 상태, 관리자 조회 경계 |

## 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 3D 안내도 구현 (완료) | 안내도 배치·입체 형상·카메라 조작과 실제 이동 좌표 연결을 함께 확인 |
| 2 | 공통 상태·추천 계약과 추천 서버 우선 구현 | 계약 문서·예제 및 로컬 모의 추천 API 완료. 선호·가상 위치·모의 시설 현황으로 추천을 계산하고 `source.kind: mock`을 표시한다. [실행·호출 예시](../lotteworld/README.md#로컬-추천-api) |
| 3 | 연속 시연 엔진 및 서버 연동 | 유입·퇴장·실제 줄·운행·반복 이용·배속·장시간 실행을 검증하고, 모의 상태 대신 시뮬레이션 상태로 추천·수락·이동을 연결 |
| 4 | 영상 입력·인원 추정과 표지판 대응 | 표지판별 영상 수신·촬영 시각·구역 대응, 표본 정답과 사람 수 오차 평가, 단절·지연 처리. 녹화 영상 검증과 실제 장치 연동을 구분 |
| 5 | 사용자 웹과 관리자 대시보드 | QR 세션·선호·추천/수락 보상과 사용자용 3D 지도, 관리자 표지판별 영상·시설 현황 조회. 양쪽 3D 화면은 같은 캐릭터 상태에 연결 |
| 6 | 전체 연결과 추천 효과 평가 | 영상 변화 → 관측 갱신 → 추천 변화 → 양쪽 화면 반영을 검증. 안내 없음/추천 적용을 같은 수요·시설 조건에서 비교하고 관측 오차·갱신 지연도 평가 |

계약·추천 서버는 시뮬레이션 완료까지 미루지 않는다. 모의 입력으로 실행되는 기능과 실제 시뮬레이션·영상 연동 완료는 구분한다. 단계 3의 장시간 연속 실행 검증은 엔진 범위의 완료이며 최종 제품 전체 완료가 아니다. 추천 효과의 실험은 실제 추천 서비스와 연결한 뒤 별도로 수행한다.

## 남은 결정

- 물리적 대기열·운행이 연결된 뒤 혼잡도와 실제 2시간 연속 실행의 부하 조건을 검증한다. 배경 순환 단계의 인원·체류·배속은 조절 가능한 시연용 설정으로 두었다.
- 추천 가중치·데이터 유효기간·세션 수명. 공통 계약의 `baseline-v1`과 수명 수치는 개발용 가정이며 최종 확정값이 아니다.
- 현장 표지판 설치 위치와 카메라 관측 구역, 수락 보상 지급량·한도·취소/회수 정책.
- 사용자용 3D 지도의 모바일 조작·화면 구성·성능 조정, AWS 허용 서비스와 배포 구성.

- 시뮬레이션·관리자 앱 통합 여부: 동일 앱의 탭 구성 제안. 최종 확정 전이다.
- 영상 전송 방식·표지판/카메라 수·시야와 관측 구역·분석 주기·서버 환경·사람 수 추정 모델.
- 밀집도 면적 보정·카메라 중복 구역 처리·영상 누락 시 추천에 쓸 대체 규칙.
- 실제 대기시간의 입력 출처와 추정 방식, 시설 운행·점검 상태의 입력 주체.
- 실제 현장 서비스의 QR 이후 위치 갱신 방식과 추천 정책의 현장 검증. 개발용 `baseline-v1`은 전체 6개 시설, QR의 `sign-baseline-v1`은 표지판 안내 대상 3개 시설을 평가한다.
- 영상 보관 여부·기간, 관리자 인증 방식·배포 환경. 현재 단일 사용자 로컬 시연과 최종 운영자 접근을 구분해 결정한다.

미정 사항이 있다고 3D 지도 보완을 중단하지 않는다. 반대로 아직 결정하지 않은 영상·위치·대기 정보가 이미 정확히 제공된다고 전제하여 화면과 추천을 확정하지 않는다.
